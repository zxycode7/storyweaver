# AI 小说世界互动游戏：产品设计

**状态：** 产品方向稿，待用户整体纠错
**日期：** 2026-10-05
**工作名称：** 暂无

## 一句话产品定义

用户提供自己的模型访问信息和一本小说，AI 阅读并理解这本书的世界、人物和叙事规律，为它生成一种合适的可玩方式。玩家可以扮演原著角色或原创角色，自由采取行动；人物会按自身目标回应，世界记住玩家带来的改变，并能在本机保存、继续游玩。

产品的核心承诺不是“把小说套进一个固定 RPG”，而是“AI 读懂这本小说，再为它生成合适的互动故事”。首版形态为网页文字互动游戏。暂不承诺生成完整的 2D/3D 游戏、美术资产或可独立运行的游戏工程。

## 用户与价值

首要用户是熟悉 AI 工具、愿意使用自己的模型服务的小说读者。他们想进入熟悉的故事世界，也想看见角色在原著未展开的情境中如何回应自己；相比让聊天模型接着续写，他们更在意角色是否像原著、选择是否有后果，以及故事能否跨多次游玩保持连贯。

次要用户是希望在自己的作品中探索人物、支线和不同走向的作者。首版不把协作写作、多人游玩或公开发布列为核心流程。

产品要解决三个相连的问题：普通聊天难以长期维护世界状态；通用游戏规则会压平小说自身的叙事特点；玩家的行动容易只改变文字表面，没有持续的因果影响。

## 产品原则

1. **先读懂原著，再组织玩法。** 用户不用先选“都市恋爱”“玄幻”或“悬疑”等类型。AI 从原文识别重要的人物关系、目标、冲突、规则、节奏和留白，并为当前作品组合玩法。类型名称可以作为理解说明，但不作为强制模板。
2. **原著有依据，新增内容有出处。** 已写明的事实、开放的空白和玩家新创造的内容分开记录。原著未交代的内容可以生成，但不能冒充原著事实。
3. **玩家能行动，世界能回应。** 自由描述行动是共同输入方式；任务、风险、资源、关系数值和其他规则按作品需要出现。系统不强制每本小说都设置战斗、装备、经验值或血量。
4. **因果比续写长度重要。** 重要人物有自己的目标和信息范围；玩家行动会改变关系、机会和后续事件。后台推进以重要角色和关键事件为主，不让所有人物每回合机械行动。
5. **长期记忆由明确状态承载。** AI 负责理解与叙述，结构化存档记录世界变化。玩家离开后可以继续同一条故事线。
6. **用户只需提供小说和模型访问信息。** 角色、开局、口味等用选择项或自然语言微调，不要求用户先写剧情简介、世界设定或角色长表。

产品中的用户可见词汇使用“故事线”“故事档案”“故事目标”“人物关系”“近期变化”。不把整个体验称为“战役”，也不默认使用“任务线”或“角色属性”。

## 核心体验流程

### 1. 接入模型并导入小说

用户选择一个常见模型服务，或填写兼容服务的地址、模型名和密钥。上传小说文件。首版支持 `.txt` 和 `.md`，单文件上限 25 MiB；自动识别 UTF-8、GB18030/GBK、Big5 和 UTF-16 常见编码。带文字层的 PDF、EPUB 可在解析稳定后加入，扫描件 OCR 暂不保证。25 MiB 是浏览器原文解析上限，不代表整本原文每回合都发给模型。

客户端先在本机提取文本、章节和段落位置，再分批请求用户选择的模型理解整本书。上传页清楚说明：小说片段会发送给所选模型服务用于建世界和后续游玩；本产品服务端不接收原文和密钥。模型调用前展示预计请求次数和全书范围；费用估算只在能取得可信单价时显示，并标明估算范围。

### 2. AI 建立本书的可玩理解

AI 生成章节索引、人物与关系、事件时间线、世界约束、人物目标、叙事风格和适合玩家介入的位置。每个重要事实保留来源章节或段落标记、可信度和时间范围。互相矛盾的资料并列保留，低可信推断不写成确定事实。

这一步也产出一本书专属的“玩法模型”：说明故事主要靠哪些变化推动、玩家可以影响什么、哪些状态值得持续记录、风险更适合如何呈现。它可以由关系、线索、时间、身份、地位、资源或其他变量组成，不限于预先定义的题材清单，也不允许运行任意生成代码。

完成后，界面给出简短的“AI 对这本书的理解”，而不是一份必须逐条审核的长报告。用户可以用普通语言纠正，例如“人物关系应该慢慢发展”或“主角不要知道他不可能知道的事”。没有修改时也能继续。

### 3. 建立故事线

玩家从原著主角、其他重要人物和原创角色中选择身份。AI 推荐适合的故事起点；玩家可选开篇、推荐位置或指定章节。原创角色由 AI 给出轻量起始方案，用户可接受、修改或用一句话补充。

系统用整本小说建立世界索引；玩家选择故事起点，而不是声明自己读到哪一章。默认避剧透：世界索引可以包含全书事实，但玩家可见概览必须无剧透，每个行动请求只检索故事起点和当前故事章节范围内的原文事实。选择原著角色时，角色能知道什么还受故事时间点和角色自身经历约束。

原著主线作为参照；玩家初始故事默认发展自己的支线，重大行动可以造成偏离。风险默认适中，可选轻松或高压体验。强度会映射到故事适用的后果：恋爱故事可能是信任变化或错失机会，悬疑可能是线索受损，冒险故事可能是资源或安全风险。

### 4. 开始与持续游玩

进入游戏后显示入场场景、当前人物状态、故事时间和一个自然浮现的机会或张力。玩家可自由输入行动，也可采用 AI 提出的情境选项。AI 按作品的玩法模型裁定结果、推进时间、更新相关人物和事件，然后保存故事档案。

每回合先呈现故事，再用可收起的摘要显示重要变化。用户可查看“发生了什么”“谁的关系或目标变了”“为什么发生”，也可检查引用的原著章节。解释信息不持续打断剧情。

## 游戏界面

- **故事主视图：** 场景、人物对话和玩家自由行动输入框；上下文相关的选项作为辅助，不限制自由输入。
- **动态状态区：** 依据这本书的玩法模型显示重要人物、关系、线索、资源、当前位置或其他有意义的状态。没有意义的面板不出现。
- **故事线记录：** 保存近期事件、当前张力、尚未解决的关系或线索，以及 NPC 的重要幕后行动；不强制使用通用“任务日志”。
- **双轨时间线：** 一轨表示原著的重要走向，一轨表示玩家故事的走向。两者发生差异时，展示导致差异的玩家行动及受影响的人物/事件。只显示当前故事进度可见的章节，避免泄露未来事件。
- **故事档案：** 按故事线继续游玩，查看存档日期与最近进展，导出或导入档案。

“双轨时间线”是核心差异化体验之一：玩家不只看到一段新生成文本，也能看到自己的行动怎样改变后续因果。

## 世界生成与每回合运行

### 三层状态

1. **原著资料层：** 原文、章节索引和有来源的事实；视为只读依据。
2. **玩法模型层：** AI 从本书生成的叙事规律、需要追踪的状态、可接受的创作空间、风格约束和规则描述。每个规则都可以追溯到原文或明确标为设计推断。
3. **故事线状态层：** 玩家身份、当前时间、关系与资源变化、开放事件、NPC 目标、玩家造成的改写及逐回合事件记录。

原著和故事线分开保存。玩家可以改变故事走向，但不能改写导入书籍的来源资料。

### 建世界流程

1. 解析文件并切章，保存原文位置映射。
2. 按章节批次抽取原子事实、人物、关系、事件、规则和叙事风格。
3. 合并别名、时间线和关系；冲突保留双方来源，避免静默择一。
4. 推断玩法模型，选择本书真正有意义的状态变量和风险机制。
5. 检查角色、事件、时间和引用是否自洽，生成可浏览的世界索引。
6. 保存完成进度，允许网络中断后从未完成章节继续处理。

### 玩家行动循环

1. **理解行动：** 判别玩家想做什么、针对谁或什么、是否改变时间或目标；不清楚时先作出可逆的合理理解，必要时再追问。
2. **取用依据：** 通过角色、地点、时间和故事线状态检索少量相关原文片段及结构化事实；不把整本小说在每个回合重复发送。
3. **裁定结果：** AI 生成叙事、影响对象、时间变化、可能的代价、NPC 行动和状态变更提案。随机性或数值判定（如玩法确实需要）由客户端规则层执行，不让模型伪造掷骰结果。
4. **推进世界：** 推进这一个叙事节拍，让与行动有关的 NPC 按其目标和已知信息采取有限行动；时间跨度取决于玩家行动。
5. **校验并保存：** 验证角色、时间、资源范围及引用；状态采用增量变更，不接受模型覆盖整个存档。验证通过后原子保存。
6. **呈现因果：** 输出正文和简短变化摘要，附可展开的依据与变更记录。

模型返回的结构化提案至少包括正文、引用编号、时间推进、状态变更、NPC 变化、开放张力和可信度。非法引用或不符合已有硬约束的变更会被拒绝或修复；无法可靠修复时保留原状态并向玩家说明，不静默写坏存档。

## 数据、隐私与本地存档

首版采用浏览器本地优先架构，每条故事线作为一个“故事档案”保存。建议用 IndexedDB 存放小说索引、来源位置映射和故事状态，避免把长文本及历史记录塞进容量较小的 localStorage。支持手动导入、导出和恢复；暂不提供账号与跨设备同步。

API 密钥默认只在当前页面会话中保留；“在这台设备记住”作为显式选择，不放进故事档案或导出文件。浏览器直连意味着密钥会在本机浏览器环境中使用，界面应如实说明，不宣称浏览器存储能提供硬件密钥库级别的保护。

小说和玩家输入仅发送到用户配置的模型服务；产品自身不收集原文、密钥或完整提示词用于分析。调试信息默认本地化；可选产品统计只记录经用户同意的匿名行为数据，不包含小说文本和对话内容。

默认导出包包含玩法模型和故事线状态，不含 API 密钥；原始小说默认不复制进导出包。恢复时可重新选择本机小说，并通过内容哈希匹配章节索引。用户可另行选择把有权分享的原文加入个人备份，但首版不提供公开分享或小说库。

## 技术方向与约束

- **形态：** 桌面和移动浏览器均可用的响应式 PWA；离线可读本地档案，模型生成仍需网络。
- **模型接入：** 常见服务预设 + 兼容接口配置。浏览器直连要求服务端开放来源 CORS；本地开发原型额外提供仅监听 loopback 的无状态转发，用于绕过开发时 CORS，不把密钥写盘。正式托管版若需转发，必须单独设计认证、滥用限制和数据处理说明，不能暗中把密钥和小说改发给产品服务器。
- **检索：** 首版使用本地章节索引、人物/别名图谱、时间和关键词的混合检索；语义向量检索在能明确其额外数据传输和费用后再加入。
- **模型输出：** 结构化 JSON Schema、有限状态变更、失败重试和超时取消；原始模型回复作为不可信输入处理。
- **内容安全：** 小说原文只作为资料，不作为系统指令；解析内容不触发工具调用，不允许小说文本更改模型权限或数据访问范围。
- **持久化：** 每回合记录输入、来源编号、提案、校验结果和已应用的状态差异。允许用户撤销最近一回合或从上一有效存档恢复。

## 失败处理

- 文件编码或章节识别失败：保留原文件，展示预览和问题章节，允许用户调整章节切分后继续。
- 长篇或限流：逐段处理、显示进度、支持暂停续跑；限制并发与重试，避免因重试扩大费用。
- 认证、余额或服务不可用：说明具体接口错误，不把 API 密钥写入日志；保留已完成的世界资料。
- 模型输出结构不合格：最多进行有限修复；修复失败时不更新世界状态，允许重试或以只读叙事继续。
- 原著信息矛盾：保留来源差异，优先呈现为不确定性；不要自行宣称其一为正史。
- 长期记忆漂移：摘要只辅助检索，结构化事实和事件账本为状态依据；摘要失效时可从账本重新生成。
- 作品暂时无法形成可玩的规则：明确告知当前玩法模型的局限，让用户调整方向或选择较自由的互动叙事；不伪装成成熟的题材系统。

## MVP 范围

### 包含

- 用户自带模型服务信息，优先支持少量经验证的服务和浏览器可用的兼容接口。
- 导入一本不超过 25 MiB 的 TXT 或 Markdown 长篇小说，提取章节、人物、事件、世界规则和有来源的事实；显示预计模型请求次数。
- AI 根据作品内容生成专属玩法模型，不要求用户先选择题材。
- 扮演原著角色或原创角色，选择故事起点；不要求用户申报读到哪里。
- 自由行动输入、适应作品的风险/资源/关系状态、任务或开放张力。
- 重要 NPC 按目标推进；重大玩家行动可让故事从原著时间线分岔。
- 本机长期存档、继续游玩、导入导出、回合撤销。
- 原著轨迹与玩家故事线的因果差异视图。

### 暂不包含

3D 或实时动作玩法、自动生成高质量立绘/配音、多人协作、公开小说社区、跨设备账号同步、社交分享、扫描版 OCR，以及所有模型服务均可即插即用的保证。

## 质量评估与数据指标

“AI 品味小说”是核心产品假设，不能只以模型说自己理解了来验收。原型阶段选取有合法测试权的题材差异明显的文本（如恋爱/日常、悬疑、幻想冒险），邀请熟悉作品的读者做盲评，并记录结果。不同题材都用同一组评估维度，玩法规则允许不同。

核心评估维度：

- **人物可信度：** 角色选择与语言是否符合其目标、知识和性格。
- **原著贴合度：** 重要叙述是否能追溯到原文，新增内容是否被识别为新增。
- **行动能动性：** 玩家选择是否带来可辨认的差异，而不是只改变措辞。
- **连续性：** 多回合后关系、时间、物品/线索和事件是否保持一致；读档后能否继续。
- **风格感受：** 玩家是否觉得故事节奏、情绪和主题像这本书。
- **使用可行性：** 从导入到开局的时间、每本书处理费用、每回合成本和失败率。

产品指标包括：成功完成世界准备的比例、首次可玩时间、用户主动修改 AI 理解的比例、前三回合后的继续率、长会话后的恢复成功率，以及次日/七日返回率。先用真实原型建立基线，再根据基线和用户访谈设定上线门槛；不在没有数据时编造体验分数阈值。分析数据不得包含原文和对话正文。

## GitHub 参照与启发

以下项目是相邻方向，不表示它们已经验证了本产品的市场需求或乐趣。研究为 2026-10-05 的快速扫描，项目 README 中的测试和体验声明均视为作者自述。

- [斗破苍穹 AI 命运推演引擎](https://github.com/Yuan05550/doupo-ai-text-adventure)：固定小说世界，已有角色/时间线选择、结构化状态、本地存档和一致性校验。启发是状态必须由本地规则校验；差别是本产品目标为从用户小说自动形成玩法模型，而不是预制单一 IP。其 README 声称 62 项回归测试通过，仍需独立体验验证。
- [RPG-OS](https://github.com/croatianrdy2defend-create/RPG-OS)：长线 AI 主持、世界资料与当前故事状态分开、NPC 有日常目标。启发是持久化与主动角色；差别是它是文件化的通用跑团工具，不是普通读者上传小说即玩的 Web 产品。其公开 playtest 被作者说明为 AI 编写，不等同真人用户验证。
- [SillyTavern](https://github.com/SillyTavern/SillyTavern)：多模型接入、角色卡、世界书与视觉小说显示。启发是 BYOK 兼容和用户可控性；差别是连续世界模拟较多依赖提示词、扩展和用户配置。
- [Claude Corpus Engine](https://github.com/galliard5/claude-corpus-engine)：面向大型文本资料的全文/语义检索与精确记录。启发是按当前行动找出处，差别是它是资料和跑团工具，不负责自动把任意小说转成故事游戏。

产品借鉴这些项目的设计经验，不依赖或复制其小说内容、固定 IP 数据或代码。若后续确需复用代码，须逐项核对对应仓库和文件的许可证。

## 风险与待验证假设

1. **题材适配质量：** 一个模型可能把不同作品都写成相似的网文套路。需以多题材盲评和跨模型评测验证；若不足，应改善玩法模型和检索，而不是仅加更长提示词。
2. **书籍长度、模型上下文和费用：** 25 MiB 上限只保护本机解析，不代表模型处理费用可忽略；请求数随全书长度增长。需以真实长篇和目标模型测量费用、处理时长和限额恢复，并在授权前展示请求量。
3. **浏览器接口兼容：** 部分模型服务不允许网页直连。首版要实测所支持的服务组合，不能把“兼容 OpenAI API”误当作“浏览器一定可调用”。
4. **隐私与原文权利：** 玩家需知道小说内容会交给所选模型服务。首版只处理用户主动提供的文本，不托管公共小说；上线前需审查服务商条款、目标地区要求和用户授权流程。
5. **AI 可能擅自编造：** 对原著引文、结构化状态和推断设置信心及来源边界；用状态验证、回合日志和撤销保护存档。
6. **玩法模型过于复杂：** 只追踪会改变玩家决策或后果的状态；无用数值和后台代理会增加成本而不增加乐趣。

## 商业模式假设

BYOK 模式让用户直接承担模型调用费用，降低产品推理成本但提高首次配置门槛。首版可用免费或低门槛方式验证用户是否愿意反复游玩；付费方向应围绕更好的建世界工作流、跨模型兼容、本机档案管理与可选同步服务探索，而不是假定用户愿为“生成了更多字”付费。定价在真实留存与模型成本数据出来前不定案。

## 分阶段计划

1. **体验验证原型：** 用少量、权利清晰的不同题材文本验证读懂原著、生成玩法模型、玩家行动造成持续后果这三个环节；先测可玩性和连贯性。
2. **单人 Web MVP：** 上线 BYOK、小说导入、世界索引、角色/起点选择、自由互动、本地故事档案和分岔视图。
3. **质量扩展：** 依据盲评和实际用户记录改善角色准确性、长篇检索、费用透明、错误恢复和更多模型适配。
4. **同步与分享评估：** 只有在隐私、版权、分享边界和留存价值明确后，再评估账号、云存档和公开作品功能。

## 本稿采用的设计决定

- 首版是网页文字互动游戏，核心体验为 AI 理解任意小说并生成适合该书的玩法；不先限制在单一题材。
- 玩家可扮演原著角色或原创角色，选起点；整本小说参与建世界，模型请求按故事进度逐步检索，默认发展支线但重大行动可偏离原著。
- 玩家每回合可以自由输入；目标、资源、风险和数值随作品内容生成。
- 世界状态结构化保存，NPC 有目标并按重要性推进。
- 默认为适中风险，可选择轻松或高压；允许持续故事线和本机存档。
- 首版用户提供模型服务访问信息和小说；建世界时整本小说分批发往用户选定的模型服务，档案保存在本机，可导入导出。
- 不把产品称作“战役”，不强制任务、战斗或通用属性面板。
